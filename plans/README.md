### Two surfaces, two designs — deliberately

The console gets a **form** because browser users have no text editor. The TUI
hands the file to **`$EDITOR`** because its users already have one, and
building a form inside the TUI means building a worse editor inside their
editor. It also sidesteps this project's most fragile input path: pasting a
prepared `SKILL.md` into the TUI composer, where paste shredding, caret drift,
and wrapped-row collapse have each been fixed in turn. With `$EDITOR` the TUI
is suspended and never sees the pasted bytes at all.

### Origin resolution: marker first, shape as fallback

Skills that predate the marker — including every one a user wrote by hand —
have no `.origin.json`. Treating them all as "not yours" would mean the Edit
button never appears for the skills it was asked for. So resolution is two
tiers: **a marker always wins**; only when absent is origin inferred from
shape (plain directory under the profile skills root, no `.clawhub.json`, slug
not bundled, not a symlink → authored).

The inference is transitional and self-healing: the first save through any
editor writes a real marker, and that skill is never shape-inferred again.

Residual risk, accepted knowingly: a third party copying a directory straight
into the profile skills root without using a RantaiClaw command reads as
authored. Nothing does this today — the one known third-party installer
(`RantAI-Copilot`) targets `<workspace>/skills/`, which the inference excludes
— and the supported install path writes a `local` marker that suppresses
inference outright.

### Found by running it, not by reading it

Two defects that no amount of plan review caught, both found in the last hour
of the effort by driving the real binary:

**`skills list` showed `---` as the description of every skill `/skill new`
creates.** `parse_yaml_frontmatter` drops empty values, so a blank
`description:` misses the lookup and `load_skill_md` falls through to
`extract_description`, which scanned from the top of the file and returned the
frontmatter fence as the first non-heading line. Latent for any skill with a
blank description — but this effort makes it the *default* state, and the
description is what the model reads to decide when a skill applies. Fixed in
#377.

**The `403` message for a pre-marker bundled skill reads "unrecorded source",
not "a bundled pack".** Correct behaviour, but worth knowing before someone
reports it as a bug: a skill installed before #375 has no marker, so it
resolves through the shape fallback, which declines it for being a bundled
slug and returns no kind at all. The refusal is right; only the wording is
less specific than it will be once markers are universal.

### Found during plan re-review

Three defects in the plans themselves, caught by verifying every claim against
source rather than trusting the draft. Recorded because two of them are live
bugs, not just planning errors.

**The API addresses skills by manifest name, which can contain spaces.**
Confirmed on a live install: a skill with `name: Name Space Probe` lists fine
and `rantaiclaw skills disable "Name Space Probe"` works, but `validate_slug`
rejects spaces (its own test asserts this, `clawhub.rs:1448`) and both
`skills_set_enabled` (`api_v1.rs:1157`) and `skills_uninstall`
(`api_v1.rs:1222`) call it on the path parameter — so both answer 400.
`skills_show` does not call it and works, so the API is inconsistent with
itself as well as with the CLI. Latent today because ClawHub slugs are already
slug-shaped; this effort ends that, since every console-authored skill gets a
human display name. Folded into 053 rather than deferred: shipping an editor
that creates skills the console cannot then disable or delete is not
acceptable.

**Open-skills entries would all report the same slug.** They are flat `.md`
files directly in `~/open-skills` and *do* carry a `location`, so
`location.parent().file_name()` yields `open-skills` for every one of them.

**`/skill edit kopi-pagi` would not have found `Kopi Pagi`.**

entrypoints depend on.

### Why the ordering changed

Three findings landed above the original feature request because they decide
whether the Knowledge Base returns anything useful:

1. **The agent only ever receives 120 characters per chunk** (plan 088).
   There is no `Tool` for the KB — the only path is shelling out to
   `kb search`, whose TOON output truncates at `CONTENT_PREVIEW_CHARS = 120`
   (`cli.rs:43`) against 800-character chunks, and discards `result.context`
   entirely. A perfect retrieval pipeline cannot help through that hole.
2. **Chunk metadata never reaches any embedding** (plan 090).
   `prepare_chunk_for_embedding` has zero production callers; all three embed
   paths use the raw chunk body. Every vector in every corpus is missing its
   category/topic/section context.
3. **GraphRAG cannot see a single LLM-extracted entity** (plan 093).
   The chunk join is `m.chunk_index = c.chunk_index`, but LLM mentions are
   always stored with `chunk_index: None`. `NULL = <int>` is never true.

### Five dead features, each with a live config knob

`prepare_chunk_for_embedding`, `generate_contextual_prefixes`
(`KB_CONTEXTUAL_RETRIEVAL_ENABLED`), `rewrite_standalone`
(`KB_STANDALONE_QUERY_ENABLED`), `format_context_for_prompt`, and `fuzzy`
resolution (`KB_INTELLIGENCE_RESOLUTION`) all have zero production callers and
full test coverage. `persona.always_on_kbs` is stored and served over HTTP and
read by nothing.

Knock-on: because contextual retrieval never runs, `contextual_prefix` is never
non-`None` anywhere — the DB column, both struct fields, the `Context:` line in
`prepare.rs`, the render in `retrieve/mod.rs:291`, and two store read paths are
all plumbing for data that does not exist.

### Why CI never caught any of it

The KB suite validates a pipeline the binary does not run.

- `tests/kb/intelligence_test.rs:320-352` seeds mentions as
  `ExtractSource::Llm` **with** `chunk_index: Some(0)` — a row shape the real
  extractor cannot produce. That is why the GraphRAG NULL join is green.
- `tests/kb/parity_test.rs` — the only retrieval-quality gate — is `#[ignore]`d,
  returns silently without a key, embeds via `prepare_chunk_for_embedding`
  (which production does not), and builds its `Retriever` with neither a
  reranker nor the intelligence handle.
- The five dead features above are each covered by passing tests.

Any plan that changes one of these must rewrite the test to drive the
production path, not just make the assertion pass. Plans 090 and 093 call this
out explicitly.

## The non-overlap rule

Plans are partitioned by **file ownership**: no two plans modify the same file,
so any two plans without a declared dependency can run concurrently in separate
worktrees without conflicting.

`src/channels/mod.rs` is the exception — too many findings live in it to split by
file. Plans 115–121 form a **serialized chain** over that one file: each declares
the previous as a dependency and must be merged before the next starts. Do not
run them in parallel.

`src/onboard/wizard.rs` is touched by 132, 133 and 142. Those three are also
serialized (132 → 133 → 142) for the same reason.

Everything else is genuinely parallel-safe.

## Running this as a loop

This effort is designed to be ground through one plan at a time by an automated
loop. The cycle per plan is:

```
pick next plan  ->  drift check  ->  implement  ->  local checks  ->  PR
   ->  PR CI green  ->  merge  ->  MAIN CI green  ->  advance
```

**The second CI check is not redundant.** Some jobs in this repo run only on push
to `main`, so a green PR does not prove a green `main`. Do not advance to the next
plan until the post-merge run is green.

### Advance criteria — the loop may move to the next plan only when ALL hold

1. The plan's own "Done criteria" checklist passes, including its mutation checks.
2. A PR exists and its CI is green.
3. The PR is merged to `main`.
4. The **post-merge** `main` CI run is green.
5. The plan's status row in this file is updated to DONE with the merge SHA.

If (4) fails, the loop stops. Do not start the next plan on a red `main` — every
subsequent plan's drift check would be measuring against a broken tree.

### Line-number drift is expected, not a stop condition

Every plan's excerpts are pinned to `f189422`. Each merge shifts them. Plans state
this explicitly: relocate by symbol name and continue. **Stop only when the code's
logic no longer matches the excerpt**, not when its position moved.
